Golden path — the happy-path walkthrough

Do these in order to exercise the full lifecycle once, start to finish. Every other route in this document is a variation, an alternative, or an admin surface off to the side of this spine.

  1. 1
    Create a session. POST /v1/sessions — kicks off threat identification then scenario generation in the background. Save the session_id from the response.
  2. 2
    Watch it run. Poll GET /v1/sessions/{session_id} (or open the live stream at GET /v1/sessions/{session_id}/events) until progress.overall reads awaiting_review.
  3. 3
    Review what was generated. GET /v1/sessions/{session_id}/results lists every proposed scenario, grouped by threat, with a decision slot on each.
  4. 4
    Decide. POST /v1/sessions/{session_id}/accept the ones you want in the register, POST /v1/sessions/{session_id}/scenarios/reject the rest. Need more or different ones first? POST /v1/sessions/{session_id}/scenarios/next-set or POST /v1/sessions/{session_id}/regenerate/scenarios.
  5. 5
    Confirm the register. GET /v1/sessions/{session_id}/accepted-scenarios shows exactly what made it in, with who-accepted-it attribution.
  6. 6
    Request a remediation plan. (Only if the risk module is enabled.) POST /v1/sessions/{session_id}/scenarios/{scenario_id}/treatment-plan for one accepted scenario, sending the register's risk-scoring fields in the body.
  7. 7
    Poll and review the plan. GET /v1/sessions/{session_id}/scenarios/{scenario_id}/treatment-plan until it's COMPLETE, then POST /v1/sessions/{session_id}/scenarios/{scenario_id}/treatment-plan/review to approve or send it back for another pass.
  8. 8
    See the whole story. GET /v1/sessions/{session_id}/audit — every step above, oldest first, with who (or the system) did each one and when.

Threat Scenario Generation & Scenario Reads

POST /v1/sessions

Kicks off a new threat-scenario-generation run for one asset: creates the session row, queues the AI pipeline on Celery, and returns immediately with a session_id to poll or stream.

Auth X-API-Key, X-User-Id, X-Entity-Id, X-Tenant-Id — all required, via Depends(get_principal); missing/blank any one -> 401 unauthorized. body.entity_id must be in the caller's single X-Entity-Id-derived entity set (principal.require_entity) -> 403 forbidden otherwise, and asset_id must be owned by that entity (dal.assert_asset_owned_by_entity) -> 403 forbidden otherwise. Optional header Idempotency-Key (<=200 chars) makes a retry with the same key+asset return the original session instead of creating a duplicate.

Implementation notes & error cases

Idempotency-Key + same (entity_id, asset_id) short-circuits to the original session (200, not 202); the same key with a DIFFERENT asset_id 409s idempotency_key_conflict, and existing_session_id names the original. supporting_system_id must be non-empty, <=50 ids, and duplicate-free -> 422 otherwise; send subsector_id (the child row), not sector_id (the parent) — swapping them historically narrowed threat-library matching silently. A body 'user_id' field is accepted but never read (unknown keys are silently ignored, not rejected — this API's bodies do NOT use extra='forbid'); the acting user always comes from X-User-Id.

Errors 401 if any auth header missing; 403 forbidden if X-Entity-Id isn't authorized for body.entity_id or asset_id isn't owned by that entity; 409 active_session_exists if the asset already has a live session and no Idempotency-Key was given (details.active_session_id names it); 409 idempotency_key_conflict if the key was reused for a different asset; 422 if supporting_system_id is invalid, or the active Config_Tuning snapshot fails its scoring-invariant check; 503 capacity_exceeded at the active-session ceiling, or a plain 503 if the Celery broker enqueue itself fails (the session is auto-cancelled first, so the id in the 503 detail is already dead).

Implementation notes & error cases

10 event types ride this stream (app/core/enums.py SSEEventType, session-scoped subset): reconcile (one-time full SessionBoard snapshot on connect, with a stitched-in "type":"reconcile" key), the 6 pipeline-lifecycle events stage_started/stage_completed/subsystem_started/session_entered_review/error/heartbeat, and the 3 best-effort advisory events next_set_result/regen_result/treatment_plan_result (never replayed, no durability guarantee — poll GET /v1/sessions/{session_id} as the source of truth). Per the route's own docstring, the native browser EventSource API CANNOT be used — it cannot set the required X-API-Key/X-User-Id/etc headers; consume with fetch() + a ReadableStream reader instead (see app/static/sse_test.html). An `error` event is NOT necessarily terminal for the session — scope="stage" means one subsystem failed while the pipeline may still finish others; wait for session_entered_review or a terminal session_status before tearing down UI.

Errors 404 if session_id unknown; 403 if outside the caller's entity scope (both checked before the stream opens, off the event loop via a threadpool); 503 sse_capacity_exceeded once sse_max_concurrent_streams concurrent streams are already open (carries a Retry-After header).

Implementation notes & error cases

mode is REQUIRED with no default — omitting it is a 422, not an implicit accept-all; scenario_ids is required (non-empty, max 50) only under mode='subset' and forbidden under 'all'/'none'. Repeatable across visits: generation already completes the session at REVIEW, so scenarios left undecided on one visit can still be accepted on a later call; re-accepting an already-accepted id is a no-op that preserves the ORIGINAL accepted_by/accepted_at (append-only, never rewritten). Naming two different VERSIONS of one scenario (e.g. a current id plus its predecessor from replaced_scenarios) in one call -> 409 with details.reason='duplicate_identity'; accept and reject are mutually exclusive per scenario.

Errors 404 if session_id unknown/wrong entity, or if a subset id can't be matched at all — details.unacceptable lists each unmatched id and why (e.g. already_accepted, already_rejected, failure_card); 409 accept_conflict with details.reason in {generation_in_progress, session_completed, session_cancelled, duplicate_identity, nothing_to_accept} depending on session state or a subset conflict; 422 if mode='subset' with empty/missing scenario_ids, or scenario_ids supplied under mode='all'/'none'.

Expensive: ~100 billed LLM paraphrase calls plus local rerank passes.

Errors 409 calibration_running if a sweep for this exact embedding+reranker pair is already in flight (response body carries details.run_id to poll instead); 401 on bad admin/API-key headers; 422 only from a malformed JSON body (e.g. force sent as a non-boolean).
